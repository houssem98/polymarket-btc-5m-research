## 2. Solution Profiles

### Profile A: Our Custom Architecture (`polymarket_btc_5m_bot`)
* **Core Paradigm**: Asynchronous Python (`asyncio`) clock-synced engine targeting the $T-10\text{s}$ to $T-3\text{s}$ snipe window.
* **Data Feed**: Binance REST/WebSocket hybrid for 1-second ticks and 1-minute klines.
* **Signal Engine**: Composite score combining Window Delta (60%), Micro-Momentum (25%), and ATR Volatility Filter (15%).
* **Execution**: Polymarket CLOB client (`py-clob-client`) with EV check ($EV \ge 0.05$), price cap ($\le \$0.88$), and minimum share size enforcement (5 shares).
* **Risk & State**: 0.25x Fractional Kelly sizing, circuit breaker on 3 consecutive losses, and `DRY_RUN` mode.

---

### Profile B: Leading Market Benchmarks

1. **`jmazzini/5m-poly-bot`**
   * **Strengths**: Asynchronous Python implementation, direction alignment check (Binance direction must match Polymarket orderbook leading side), per-asset price thresholds (stricter for BTC than ETH).
   * **Weaknesses**: Fixed poll loop without native clock-based deterministic slug calculations; relies heavily on standard HTTP threads.

2. **`Archetapp Gist / Build Guide`**
   * **Strengths**: Deterministic slug calculation (`btc-updown-5m-{window_ts}`); heavily weighted Window Delta (5-7x weight over TA indicators); auto-claim engine via Playwright; multi-run backtesting simulator (`compare_runs.py`).
   * **Weaknesses**: Single-threaded request patterns prone to Binance rate-limiting; synchronous HTTP execution instead of non-blocking websockets.

3. **`Benjam1nCup / Polymarket-trading-bot-python-V2`**
   * **Strengths**: Orderbook Liquidity Momentum — monitors Polymarket L2 depth and orderbook influence metrics instead of price action alone.
   * **Weaknesses**: High API overhead; sensitive to rapid bid/ask cancellation spoofing on the CLOB.

4. **`cryptuon/polybot` & `Novals83/5min-btc-polymarket` (OpenClaw / Skill-Based)**
   * **Strengths**: Terminal CLI, encrypted hosted vault keys, whale wallet copy trading, micro-hedging extreme orderbook skews (e.g., placing small tail bets at 95/5 skew).
   * **Weaknesses**: Generalized multi-market engine not hyper-optimized for sub-second 5-minute crypto window latency.

## 4. Identified Gaps & Missing "Secret Sauce"

To transform our bot into a market-dominant trading system, we need to address the following missing features:

### Gap 1: Real-Time Orderbook Liquidity & Depth Analysis
* **Problem**: Relying solely on Binance price delta can lead to losses if Polymarket's orderbook is depleted or priced at $\$0.96+$ before order arrival.
* **Fix**: Subscribe to Polymarket CLOB WebSockets (`wss://ws-subscriptions-clob.polymarket.com/ws/market`) to read the real-time bid/ask spread and top-of-book depth before placing IOC orders.

### Gap 2: Micro-Hedging & Tail-Risk Management
* **Problem**: Binary outcomes are prone to last-second 1-second whipsaws (e.g., a sudden $100 BTC candle at $T-2\text{s}$).
* **Fix**: Adopt the OpenClaw/polybot pattern: When orderbook odds hit extreme skews (e.g., UP is trading at 96¢ and DOWN at 4¢), allocate $1–$2 to buy the 4¢ token as a micro-hedge against severe tail-risk reversals.

### Gap 3: Automated Contract Payout Claims via Web3
* **Problem**: Manual token redemption wastes time and leaves capital tied up in ERC-1155 tokens.
* **Fix**: Integrate a direct Web3 `redeemPositions` call against Polymarket's Conditional Token Framework (CTF) contract (`0x4D97DCd97eC945f40cF65F87097ACe5EA0476045` on Polygon Mainnet) rather than relying on browser/Playwright scrapers.

### Gap 4: Latency-Optimized Multi-RPC Routing
* **Problem**: Polygon RPC public endpoints frequently experience congestion and rate-limiting during high market activity.
* **Fix**: Add multi-RPC fallback configuration (Alchemy, QuickNode, Chainstack, Ankr) with automatic low-latency routing.
